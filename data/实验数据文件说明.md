# 实验数据文件说明

## 1. 整体总结

这个文件夹保存的是一个用于评测大语言模型“知识边界 / 幻觉 / 弃答行为”的数据集发布包。  
它的核心目标不是普通问答准确率，而是观察模型在以下几类题目上的行为变化：

- `Zone A`：公众知识中较常见、较容易回答的问题
- `Zone B`：公众知识中相对不那么常见的问题
- `Zone C`：由真实公开题目改写而来的“边界题”，答案仍然存在，但更容易让模型出错或犹豫
- `Zone D`：合成的、私有式或虚构的未知题，设计目标是让模型选择弃答

文件夹主要分为三类内容：

- `pilot/`：小规模试验版数据，用来先跑通构建流程和验证思路
- `full/`：正式冻结版完整数据，用于论文或最终实验
- `docs/`：数据集说明文档

## 2. 目录级别说明

### `docs/`

- 放数据集说明文档，解释数据集的目标、构成、分区逻辑、用途和限制。

### `pilot/`

- 放试验版数据及其元数据、验证结果和字段定义。
- 总量 `240` 条，其中 `dev=120`、`test=120`。
- 只覆盖 `medicine_medmcqa`、`multi_hop_hotpotqa`、`science_sciq` 三个域。

### `full/`

- 放完整正式版数据、统计、验证结果、字段定义以及 contamination 审核文件。
- 总量 `1200` 条，其中 `dev=120`、`test=1080`。
- 覆盖 `commonsense_commonsenseqa`、`general_triviaqa`、`medicine_medmcqa`、`multi_hop_hotpotqa`、`science_sciq` 五个域。

## 3. 每个文件分别是做什么的

### 根目录

- `.DS_Store`
  - macOS 自动生成的文件夹显示缓存文件。
  - 与实验数据本身无关，可以视为系统杂项文件。

### `docs/`

- `docs/dataset_card.md`
  - 数据集总说明文档，作用相当于“发布说明 + 使用说明”。
  - 里面写清了数据集目标、区间定义（A/B/C/D）、来源、划分方式、字段列表、预期用途和局限性。
  - 如果你之后要写论文附录、数据说明或 README，这个文件是最核心的解释文件。

### `pilot/`

- `pilot/pilot_metadata.json`
  - 试验版数据集的元数据总表。
  - 记录了试验版的规模、`dev/test` 数量、包含哪些 domain、各 zone 数量、污染风险分布、题目来源分布、构建规则和随机种子。
  - 它更像是“pilot 数据是怎么配置出来的”的摘要。

- `pilot/schema.json`
  - 试验版数据的字段清单。
  - 规定每条样本应该有哪些字段，比如 `question_id`、`zone`、`question_text`、`gold_answer`、`contamination_risk`、`abstention_expected` 等。
  - 用途是保证下游读取、验证和评测脚本知道样本结构。

- `pilot/pilot_dev.jsonl`
  - 试验版开发集，`120` 条。
  - 每行是一条 JSON 样本，用于开发阶段调试评测流程、prompt、解析器或分析脚本。
  - 从样例看，里面既有真实公开题，也有 `Zone D` 的合成未知题。

- `pilot/pilot_test.jsonl`
  - 试验版测试集，`120` 条。
  - 结构和 `pilot_dev.jsonl` 一样，但用于 pilot 阶段的正式测试或小规模验证。
  - 可以理解为“在小数据上先验证 benchmark 是否可用”的主测试文件。

- `pilot/pilot_validation_report.json`
  - 试验版验证报告。
  - 用来确认 pilot 数据构建是否正确，例如样本总数、分区数量、`abstention_expected` 数量、是否缺字段、schema 是否通过。
  - 这是一个质量检查文件，不是训练或评测输入文件。

### `full/`

- `full/schema.json`
  - 正式版完整数据的字段清单。
  - 字段与 pilot 基本一致，说明最终发布版沿用了统一的数据结构。
  - 用途同样是给读取、验证、评测代码提供结构约束。

- `full/dev.jsonl`
  - 正式版开发集，`120` 条。
  - 用于正式 benchmark 中的开发调试、prompt 调整、解析规则测试、指标脚本联调。
  - 样本覆盖多个 domain 和不同 zone。

- `full/test.jsonl`
  - 正式版主测试集，`1080` 条。
  - 这是完整 benchmark 中最核心的数据文件，通常也是最终模型评测最主要的输入文件。
  - 如果你要复现实验主结果，这个文件通常最关键。

- `full/dataset_stats.json`
  - 正式版统计摘要文件。
  - 记录正式版的总量、各 zone 数量、污染风险分布、题目来源分布、domain 列表和随机种子。
  - 用途是快速查看数据集构成，而不用把 `jsonl` 全量扫一遍。

- `full/full_validation_report.json`
  - 正式版验证报告。
  - 检查正式发布版是否通过结构和数据质量校验，例如是否缺字段、是否有重复 `question_id`、schema 是否正确、污染审核文件是否齐全。
  - 这个文件主要服务于“发布前自检”和“可复现性说明”。

- `full/audit_contamination_low.jsonl`
  - 正式版中 `contamination_risk = low` 的样本子集，共 `457` 条。
  - 作用是给 contamination 审核或分层分析使用，方便单独检查低污染风险样本。
  - 本质上是从正式数据中按污染风险切出的审计文件，而不是独立的新数据集。

- `full/audit_contamination_medium.jsonl`
  - 正式版中 `contamination_risk = medium` 的样本子集，共 `155` 条。
  - 用于中等污染风险样本的单独审查、抽样检查或分层统计分析。

- `full/audit_contamination_high.jsonl`
  - 正式版中 `contamination_risk = high` 的样本子集，共 `588` 条。
  - 用于高污染风险样本的重点审查，因为这部分最可能与公开题源在表述上高度相似。
  - 如果后面要分析“模型成绩是否受题源污染影响”，这个文件会很重要。

## 4. 这些文件在实验流程里的关系

可以把它理解成下面这条链路：

1. `schema.json`
   - 先定义每条数据应该长什么样。

2. `pilot_*.jsonl` / `full/*.jsonl`
   - 再提供真正用于实验的数据样本。

3. `pilot_metadata.json` / `dataset_stats.json`
   - 再用统计摘要文件说明“数据集整体长什么样”。

4. `pilot_validation_report.json` / `full_validation_report.json`
   - 再用验证报告证明“数据格式和基本质量检查通过了”。

5. `audit_contamination_*.jsonl`
   - 最后补充污染风险分层审计文件，便于做 contamination-aware 分析。

## 5. 一句话判断哪些文件最关键

如果你只是想知道“实验真正跑的是哪些数据”，最关键的是：

- `full/test.jsonl`
- `full/dev.jsonl`
- `docs/dataset_card.md`

如果你想知道“这个数据集是怎么构造和校验的”，最关键的是：

- `pilot/pilot_metadata.json`
- `full/dataset_stats.json`
- `pilot/pilot_validation_report.json`
- `full/full_validation_report.json`
- `pilot/schema.json`
- `full/schema.json`

如果你想专门分析“污染风险 / contamination”：

- `full/audit_contamination_low.jsonl`
- `full/audit_contamination_medium.jsonl`
- `full/audit_contamination_high.jsonl`
